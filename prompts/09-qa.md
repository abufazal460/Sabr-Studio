# 09-qa.md — Sabr Studio End-to-End QA

Companion to `00-master-context.md` (full source hierarchy, scope, route table, functional non-negotiables) and `01-setup.md` (repo shape, environment/tooling). This is a **test-and-report prompt, not an implementation prompt**: its job is to verify actual, running behavior against what's already documented, fix only confirmed failures, and retest every fix. It does not invent a pass/fail criterion that isn't grounded in the source hierarchy.

---

## 1. Role & Objective

You are running full end-to-end QA on Sabr Studio against the scope, routes, and non-negotiables already fixed in `00-master-context.md`. Every check below is executed against the actual running application (or actual code, where a live environment isn't available) — never assumed to pass because the code "looks right."

---

## 2. Source of Truth

`00-master-context.md` §3 hierarchy applies: `PRD.md` → `TRD.md` → `ARCHITECTURE.md` → `UI-UX.md`/`ANIMATION.md` → `DATABASE.md` → `API.md` → `SECURITY.md` → `DEPLOYMENT.md` → `CODING-RULES.md`/`AI-RULES.md` → `QA-CHECKLIST.md` → existing repo → current task. This file draws its pass/fail baseline from Master Context §5 (scope, routes), §6 (implementation requirements), §7 (constraints), and `01-setup.md`'s approved stack/env boundary. Where a check needs finer detail neither file states (an exact component's visual spec, an exact copy string), verify against the actual implemented/documented behavior elsewhere in the source hierarchy if accessible — do not fabricate an expected result.

---

## 3. Method & Failure Report Format

- **Test actual behavior.** Click the button, submit the form, hit the endpoint, resize the viewport — don't infer a pass from reading the component.
- **Fix only verified issues.** A suspicion is not a bug until reproduced.
- **Retest every fix** — a fix isn't done until the original repro step now produces the expected result.
- **Never mark incomplete or unverified work as passed.** If something can't be tested in the current environment, report it as **Unable to Verify**, not as a pass.

Every failure is reported in this exact block:

```
Issue: <one-line description>
Reproduction: <exact steps — route, action, input>
Expected: <what should happen, per the source hierarchy>
Actual: <what actually happened>
Location: <file/component/endpoint>
Fix: <the minimal correct change>
Retest: <the repro steps re-run after the fix, with the resulting outcome>
```

## 4. Checklist

### 4.1 Public Routes
Verify every route in Master Context §5's public table loads correctly and renders the right page: `/`, `/projects`, `/projects/:slug`, `/retail`, `/retail/:slug`, `/services`, `/about`, `/contact`, `/cart`. Verify an unmatched URL renders a 404, and a matched-but-invalid `:slug` (deleted/unpublished/nonexistent) renders the page's own not-found state rather than a crash or the generic 404.

### 4.2 Admin Routes
Verify every route in Master Context §5's admin table: `/admin/login`, `/admin`, `/admin/projects`, `/admin/retail`, `/admin/enquiries`, `/admin/orders`. Verify an unauthenticated visit to any protected admin route redirects to `/admin/login`, and that direct API access (not just UI navigation) to `/api/admin/*` without a valid session is independently rejected (Master Context §6.5).

### 4.3 Navigation
Verify every nav link (desktop and mobile) points to a real, correct route with no dead links, and that the active route is indicated. Verify the Navbar "Login" control's actual current behavior matches whatever was explicitly confirmed for it — if it's still unwired pending confirmation (Master Context C2), verify it does nothing destructive/misleading rather than silently landing on an unconfirmed destination.

### 4.4 Buttons & Links
Verify every interactive control performs its documented action (submit, navigate, add-to-cart, remove, load-more, etc.), is keyboard-operable, and produces no dead click (a button that does nothing, or a link with no `href`/route target).

### 4.5 Forms
Verify every form (enquiry, checkout contact fields, admin login, admin CRUD forms) through its full submission lifecycle: initial state, client-side validation error, submitting/disabled state, success confirmation, failure with data preserved for retry. Verify the enquiry form specifically enforces `email` as required (C4) and does not submit or persist a `projectType` field unless that conflict (C5) has been explicitly resolved.

### 4.6 Projects
Verify the public listing and detail pages reflect only published projects, that "View All"/load-more behavior matches the documented paging approach, and that admin create/edit/delete/publish actions on Projects are reflected correctly on the public site.

### 4.7 Retail
Verify the public listing and detail pages reflect only published + available items, that category filtering (if present) works, and that admin create/edit/delete/availability changes on Retail items are reflected correctly on the public site.

### 4.8 Enquiries
Verify a submitted enquiry is persisted to MongoDB even when the email-notification step is forced to fail (Master Context §6.7 — the two are independent), and that `Enquiry` records are never reachable via any public endpoint. Verify admin enquiry management (list/detail/status update/delete) works and is protected.

### 4.9 CRUD (Admin — Projects/Retail/Enquiries/Orders)
Verify Create, Read, Update, Delete for each admin-managed resource actually persists and reflects correctly, that a new/edited image goes through the documented upload path (§4.11), and that deleting a Project/Retail item doesn't leave the public site in a broken state (dangling references, 500s on the now-missing slug).

### 4.10 Authentication
Verify login with correct credentials succeeds and sets the expected cookie; incorrect credentials fail with a generic message (Master Context §6.5); `GET /api/auth/me` correctly reflects session state; logout actually ends the session (a subsequent `/api/auth/me` call returns unauthenticated).

### 4.11 Authorization
Verify every `/api/admin/*` endpoint independently rejects a request with no/invalid session, tested directly against the API (not only through the UI) — per-route, not just for one representative endpoint.

### 4.12 Uploads
Verify an admin image upload (Projects/Retail) actually results in a Cloudinary-hosted asset with only `{url, publicId}` stored in MongoDB (Master Context §6.8), that invalid file types/sizes are rejected client- and server-side, and that deleting the parent record triggers the Cloudinary cleanup path.

### 4.13 API Responses
Verify responses match the uniform envelope (`{success, data}` / `{success, message, errors?}`) and correct status codes (400/401/403/404/409/500) across a representative sample of endpoints, not just the happy path.

### 4.14 Validation
Verify server-side validation is genuinely authoritative by sending a request that bypasses/violates client-side validation directly (e.g., missing required field, malformed email) and confirming the backend still rejects it.

### 4.15 Loading / Empty / Error / Success States
For every data-dependent view (Projects/Retail listing & detail, Cart, admin lists), verify: a loading indicator appears while the request is in flight (never a blank screen), an empty result set shows an empty state rather than fabricated placeholder content, a forced API failure shows a non-crashing error state, and a successful result renders correctly. No view is left permanently spinning on failure.

### 4.16 Responsiveness
Test at minimum: **320, 360, 375, 390, 414, 480, 640, 768, 1024, 1280, 1440, 1920, and representative widths between 2560–3840px** (Master Context §5 requires 320px–3840px support). At each: no horizontal scroll on normal content, no stretched/cropped images, nav collapses/expands at the correct breakpoint, touch targets remain usable, admin tables scroll within their own container rather than the page.

### 4.17 Accessibility
Verify against the WCAG 2.2 AA target named in Master Context §6.10: keyboard reachability and visible focus on every interactive element, real `<label>`s on form fields, `aria-label` on icon-only controls, `aria-describedby`-linked validation errors, no color-only signaling, correct focus management on modal/drawer open-close (focus moves in, returns to trigger on close), semantic HTML structure with one `<h1>` per page.

### 4.18 SEO
Verify each indexable public page has a unique `<title>` and meta description, a correct canonical URL derived from one site-URL source, and that Project/Retail detail pages carry the resource's own title/description rather than a stale or duplicated value. Verify `robots.txt`/sitemap reflect actual publish state if reachable, and that not-found views don't inherit a prior page's metadata.

### 4.19 Animations
Verify the documented library boundary is actually respected in practice — scroll-position-driven effects don't stutter or double-fire, component-scoped animations (modals, hover, mount/unmount) behave correctly, and no route-transition animation exists (Master Context §6.9 explicitly excludes this). Verify `prefers-reduced-motion` measurably reduces/removes decorative motion without hiding functional content or controls.

### 4.20 Performance
Verify pages load without obviously unoptimized behavior: images aren't served at drastically larger sizes than displayed, the admin bundle isn't loaded on public pages (Master Context's lazy-loading intent for the admin tree), and no obviously redundant duplicate network requests fire on a single page load.

### 4.21 Security
Cross-check the security-relevant non-negotiables actually hold in the running app: no secret in the frontend bundle or response bodies, cookie-based auth flags correct, rate-limiting actually triggers on repeated login/enquiry/checkout attempts, payment amount is never accepted from the client, an empty cart is rejected server-side at checkout. Deep security review beyond this spot-check belongs to a dedicated audit — flag anything suspicious rather than exhaustively re-deriving it here.

### 4.22 Console & Network Errors
On every route tested (§4.1–4.2), check the browser console and network tab for uncaught JS errors, failed asset loads (404s on images/fonts/scripts), and unexpected 4xx/5xx responses during normal navigation — a page can "look fine" visually while still throwing errors that indicate a real defect.

## 5. Constraints

- Do not report a failure you haven't actually reproduced — a code-review suspicion goes in a separate "needs investigation" note, not the failure list, until reproduced.
- Do not fix anything beyond the verified issue itself — no unrelated refactors, renames, or "while I'm in here" changes (Master Context §7, §9.3).
- Do not weaken a control to make a test pass (e.g., disabling validation or rate-limiting to get past it) — if a control blocks a legitimate test flow, that's itself a finding to report, not something to route around silently.
- Do not silently resolve a Section 4 conflict (C1–C7) differently from its stated resolution while testing code that touches it — flag it if surfaced.
- Do not claim a responsive/accessibility/SEO check passed at a breakpoint or page you didn't actually test.

---

## 6. Completion Criteria

QA is complete only when:
1. Every item in §4 has been actually tested (not assumed) and resulted in a Pass, a reported Failure (§3 format), or an explicit Unable to Verify.
2. Every reported failure that was fixed has been retested against its original reproduction steps, with the outcome recorded.
3. No fix altered unrelated functionality or weakened an existing control.
4. Responsive testing covers the full documented range (320px–3840px) at the widths named in §4.16, not a partial subset presented as complete.
5. No incomplete, unverified, or partially-working feature is reported as passed.
